# Session 2026-06-05

## Phase 3, Feature 1: Role-based Presets ✅

### Summary
Implemented role-based preset contracts. Different opencode roles (developer, architect, qa-engineer, etc.) now automatically get different default contract bundles when activated. The `profiles` top-level field serves as fallback for unmapped roles.

### Changes

#### `src/config/schema.ts`
- Added `roleProfiles?: Record<string, string[]>` field to `ConfigSchema`

#### `src/rules/presets.ts`
- Added `ROLE_PROFILES` — built-in role→profile mappings:
  - `developer` → `['socratic']`
  - `architect` → `['socratic', 'architecture']`
  - `qa-engineer` → `['socratic']`
  - `devops-engineer` → `['socratic']`
  - `product-owner` → `[]`
  - `business-analyst` → `[]`
  - `technical-writer` → `['socratic']`
  - `ux-designer` → `[]`
  - `data-scientist` → `['socratic']`
  - `consultant` → `[]`
  - `team-lead` → `[]`
  - `educator` → `['socratic']`
- `default` role intentionally absent → falls through to top-level `profiles` field
- Added `getRoleProfiles(role, userRoleProfiles?, fallbackProfiles?)` with resolution order:
  1. User-specified override (`roleProfiles` in YAML)
  2. Built-in defaults (`ROLE_PROFILES`)
  3. Top-level `profiles` fallback
  4. Empty array `[]`

#### `src/config/loader.ts`
- `LoadedConfig` gains:
  - `baseContracts: StructuralCouplingContract[]` — user-defined contracts (always active)
  - `roleProfiles: Record<string, string[]>` — merged built-in + user overrides
- `load()` now:
  - Stores base contracts separately from profile-derived contracts
  - Merges built-in `ROLE_PROFILES` with user `roleProfiles` overrides
  - Resolves initial `contracts` for 'default' role (backward compatible)
- `getActiveContracts(role)` now:
  - Looks up role→profiles in merged roleProfiles
  - Falls back to top-level `profiles` field
  - Resolves profiles to preset contracts
  - Merges with base contracts (user overrides profile contracts by ID)

#### `src/rules/engine.ts`
- Added `ContractResolver` type: `(role: string) => StructuralCouplingContract[]`
- Constructor accepts optional second parameter `contractResolver`
- `setRole(role)` now:
  - Updates `state.role`
  - If resolver is provided: calls it, re-sorts contracts (BLOCK first), reloads

#### `src/index.ts`
- Passes `config.getActiveContracts.bind(config)` as resolver to `new RuleEngine()`

### Backward Compatibility
- All existing 72 tests pass unchanged (after updating inline `LoadedConfig` objects in test files)
- Existing configs without `roleProfiles` field work as before
- Top-level `profiles` field still works as the primary mechanism
- Engine's `setRole()` without resolver works as before (no contract reloading)

### Design Decisions
1. `default` role excluded from `ROLE_PROFILES` so top-level `profiles` always works as fallback
2. `ContractResolver` is optional parameter — engine works identically without it
3. User override wins over built-in per-role (not additive, to allow opting out)
4. Base contracts always returned for any role (role-independent)
5. BLOCK priority maintained on every re-resolution
